# 目的

实现与审查通过后收口：让说明系统（AGENTS.md、.docs/ 与相关索引）与当前实现重新对齐，形成可核对的证据摘要（含未验证项与残余风险），列出遗留项。提交与推送是独立的用户决策，不是收尾的默认动作。

# 何时进入

代码改动已通过复核（`task` 调用 `agent: reviewer`），或用户直接要求收尾。尚无任何验证证据时，先回到实现/验证，不进入本 Skill。

# 前置输入

- 本次改动、验证证据（测试、typecheck、命令输出、真实表面路径）。
- 若存在：本次的 `.specs/tasks/<task-id>.md` 与 `.plans/<task-id>.md`。
- `AGENTS.md` 与 `.docs/` 的现有内容（判断哪些说明已过时）。

# 执行步骤

1. 刷新实现侧文档：更新 `.docs/` 中因本次改动而过时的部分。它们记录「系统当前怎么运行」，长期约束仍留在 `.specs/domain/`。
2. 若本次改动改变了项目约定入口（`AGENTS.md` 里的命令、架构边界、交接清单），同步更新。
3. 归档任务文档（仅当 `.specs/`、`.plans/` 存在且本次使用了它们）：在对应文档 frontmatter 标 `status: done`；没有 frontmatter 则补一段。简单路径（无 Task Spec/Plan）跳过本步。
4. 写证据摘要，固定五要素：改了什么；已验证什么（命令与结果）；未验证或不确定什么；残余风险；遗留项。全链路任务注明依据哪份 Task Spec、受哪些 Domain Spec 约束。
5. 长任务或跨会话任务记录决策轨迹：phase / decision / why / evidence / result，写进现有 run artifact 或文档，不新建 Skill，并在摘要里给出路径。
6. 若可用，调用 `task`（`agent: reviewer`）审计「结论 vs 证据」：没有运行证据的结论标 `inferred`，不得写成已验证。
7. 关闭本次会话中仍在进行的 todo，只保留确有后续动作的项。
8. 提交（条件动作）：仅当用户明确要求提交或推送时执行。
   - 先 `git status` / `git diff` 核对范围，不夹带无关改动。
   - 当前分支是 `main`/`master` 时先问用户是否新建分支；分支名与提交信息遵循仓库既有约定，不自行发明前缀。
   - 提交信息可用 `/commit` 生成后再确认；需要联网的推送单独执行，遇到认证问题按失败上报。
   - 用户未要求时，**不提交、不推送、不改写历史**。
9. 列出遗留项（未覆盖的边缘、后续建议），不擅自扩大范围。所有写操作与命令按 omp 的审批流程执行，不试图绕过。

# 产出物

- 刷新后的 `AGENTS.md` / `.docs/`（如有必要）。
- 已归档的 Task Spec 与 Plan（若项目使用 `.specs/` / `.plans/`）。
- 证据摘要（五要素）。
- 遗留项清单。
- 提交记录（仅当用户明确要求）。

# 退出条件

说明系统与实现对齐，证据摘要完整且区分已验证与 inferred，遗留项已显式列出；若用户要求提交，提交在确认过的分支上完成且推送范围与用户要求一致；未获授权时，仓库里没有任何本次新增的提交或推送。
